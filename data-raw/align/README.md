# Align reads and collect quality control data

Aligns the preliminary data:

- All programs are installed by the [spack][spack-url] environment file,
  `spack.yaml` as follows:
   ```bash
   spack env activate .
   spack install
   ```

- The dependency graph order of operations to run the programs are set
  by the [ninja-build][ninja-url] file `build.ninja`.  The
  `build.ninja` file in not added to the git repository here because
  it is generated by the template `build.ninja.j2` with data from
  `build.ninja.json` as follows:
   ```bash
   spack env activate .
   spack load py-jinja2-cli
   jinja2 \
	   --strict \
	   -D prefix_data=$HOME \
	   -D mem_thread_mb=$((7 * 1024)) \
	   -D nproc=$(nproc) \
	   build.ninja.{j2,json} > build.ninja
   ```

- Then one can run ninja to run all the programs:
   ```bash
   spack env activate .
   for spec in $(spack find -r | sed -E -n -e '/[+]/s/[[][+][]]//p'); do
	   spack load $spec
   done
   ninja -v |& tee ninja-v-$(date -Is).log
   ```

> [!NOTE]
> One of the limitations with using `ninja` is that it runs jobs as
> soon as input files exist and only honors CPU constraints but not
> memory constraints.  As a workaround, using a `pool` limits single
> running process for multi-threaded jobs like `align` and
> `feature-counts`.  For a more resource constrained environment, such
> as continuous integration or a shared server accommodating multiple
> users, work is in progress to use [flux][flux-url] to honor both
> memory and CPU constraints as well as multiple users with
> hierarchical scheduling.

[spack-url]: <https://spack.io/>
[ninja-url]: <https://ninja-build.org/>
[flux-url]: <https://flux-framework.org/>
